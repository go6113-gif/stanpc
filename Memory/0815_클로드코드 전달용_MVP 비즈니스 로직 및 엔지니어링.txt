0815_클로드코드 전달용_MVP 비즈니스 로직 및 엔지니어링 상세 명세서

**[클로드 코드(Claude Code) 개발 전달용] StanPC MVP 비즈니스 로직 및 엔지니어링 상세 명세서**

이 문서는 StanPC MVP의 프론트엔드/백엔드 재구축 및 2차 확장을 위한 최종 시스템 아키텍처, 데이터베이스 스키마, 비즈니스 로직, 그리고 법무 검토안을 포함하는 상세 명세서입니다.

---

## 1. 인벤토리 상태 관리 스키마 (Inventory State Machine)

K-POP 포토카드 수집가의 실제 라이프사이클을 반영하여 단순 이분법(Have/Want)을 대체하는 4단계 상태(Status)와 3대 거래 의사(Intent) 로직입니다.

### 1.1. 데이터베이스 스키마 (Supabase PostgreSQL)

`user_inventory` 테이블에 다음 컬럼 및 데이터 타입을 적용합니다.

* `status` (ENUM): `'OWNED'`, `'INCOMING'`, `'TRADING'`, `'WISH'`
* `trade_intent_wtt` (BOOLEAN): 기본값 `FALSE` (교환 희망)
* `trade_intent_wts` (BOOLEAN): 기본값 `FALSE` (판매 희망)
* `trade_intent_wtb` (BOOLEAN): 기본값 `FALSE` (구매 희망, `WISH` 상태에서만 활성화 가능)
* `target_price` (DECIMAL): WTS 활성화 시 입력된 판매 희망가 (NULL 허용)
* `currency` (VARCHAR): `USD`, `KRW`, `JPY` 등 (기본값 `USD`)

### 1.2. 상태 전이(State Transition) 프론트엔드 로직

* **Incoming ➔ Owned:** 유저가 '수령 완료' 버튼 클릭 시 상태가 즉시 업데이트되며, 해당 카드의 소장 타임스탬프(`minted_at`)가 생성됩니다.
* **WTT/WTS 활성화 제약:** `status`가 `OWNED`인 카드만 활성화 가능하며, `TRADING` 상태 진입 시 해당 카드의 WTT/WTS 토글은 수정 불가(Lock) 처리됩니다.

## 2. 디지털 보유 증명 (Proof-of-Collection) 파이프라인

단순 캡처본을 걸러내고 디지털 보증서를 발급하는 4중 인증 엔진입니다.

### 2.1. 검증 및 발급 백엔드 로직

1. **EXIF 검증 (Client -> Server):** 업로드 전 클라이언트에서 `exif-js` 등을 통해 메타데이터를 파싱. `DateTimeOriginal` 및 `Model`(카메라 기종) 값이 존재하지 않으면 '메타데이터 없음(Unverified)' 플래그 처리.
2. **pHash 생성 (Server):** 업로드된 이미지에서 Perceptual Hash(pHash)를 생성하여 `inventory_hashes` 테이블에 저장. 기존 해시값과 Distance 검사를 통해 허용 오차 이하의 중복 이미지 발견 시 업로드 차단 또는 '도용 의심' 플래그 처리.
3. **인증서 발급:** 검증 통과 시 `STPC-YYYY-UUID(앞 8자리)` 포맷의 고유 식별 번호를 생성하여 `inventory_certificates` 테이블에 매핑.

### 2.2. SNS 공유 카드 렌더링 (Canvas/WebGL)

* 유저가 '공유' 버튼 클릭 시, 클라이언트 단의 HTML5 Canvas API를 활용하여 다음 레이어를 실시간 병합 후 다운로드(`Blob`)합니다.
* **Layer 1:** 블랙/골드 프레임 배경 (1:1 또는 9:16 비율)
* **Layer 2:** 유저가 업로드한 포토카드 이미지 (가운데 정렬, 3D 틸트 CSS 효과 캡처)
* **Layer 3:** 인증 씰(Seal), 시리얼 넘버, 타임스탬프, 유저 닉네임, 랜딩 QR 코드.

## 3. 티어별 분기 및 클라이언트 리소스 최적화 로직

서버 스토리지 비용(R2) 최적화와 유료 전환 유도를 위한 티어별 강제 분기 로직입니다.

### 3.1. 이미지 압축 로직 (`browser-image-compression` 적용)

업로드 컴포넌트에서 유저의 현재 구독 상태(`subscription_tier`)를 확인하여 압축 파라미터를 동적으로 적용합니다.

* **Free Tier (무료 회원):**
* `maxSizeMB`: 0.06 (60KB)
* `maxWidthOrHeight`: 854 (480p 수준)
* `useWebWorker`: true


* **PRO Tier (유료 회원 - 720p 기본/최대 4K):**
* 유저가 선택한 해상도 옵션에 따라 분기. (기본 720p 권장 시 `maxWidthOrHeight`: 1280)
* `maxSizeMB`: 최대 1.0 (고해상도 허용)



### 3.2. 업로드 한도 제어 (Limit Check)

* 업로드 API 라우트 호출 시 Supabase에서 현재 유저의 `inventory_count`를 조회.
* 무료 회원이고 카운트가 50 이상일 경우 HTTP 403 반환 및 프론트엔드에서 Paywall 모달(`Upgrade to PRO`) 트리거.

## 4. [신규] 초헤비 유저 제한 (Fair Use Policy) 약관 및 로직

'평생 소장'이나 '무제한 확장'을 약속하더라도, 매크로 봇이나 악의적 스크래핑, 과도한 서버 리소스 낭비를 막기 위한 시스템적 하드 리미트(Hard Limit)가 필수적입니다.

### 4.1. 약관(TOS) 명시 사항

* **공정 사용 정책 (Fair Use Policy):** "StanPC는 유저의 원활한 컬렉션 관리를 위해 대용량 스토리지를 제공하나, 서버의 안정성을 저해하는 비정상적인 대량 업로드(API 우회, 봇 사용) 및 1인당 통상적 수집 범위를 초과하는 극단적 스토리지 점유(예: 단일 계정 내 포토카드 20,000장 초과 또는 일일 업로드 500장 초과)가 감지될 경우, 사전 안내 후 계정 제한 및 추가 비용이 청구될 수 있습니다."

### 4.2. 시스템 제어 로직 (Rate Limiting)

* **일일 업로드 제한:** 단일 유저의 24시간 내 업로드 횟수를 500장으로 제한 (Cloudflare Rate Limiting 또는 Supabase Edge Function에서 차단).
* **볼트 하드 캡 (Hard Cap):** 평생권 $12 기본 1,000장 / 최대 증설 슬롯을 포함하더라도 시스템상 최대 안전 한도를 20,000장으로 설정. 이를 초과하는 업로드 시도 시 `ERR_FAIR_USE_LIMIT_EXCEEDED` 반환.

## 5. 슈퍼 컬렉터 챌린지 랭킹 및 롤다운 알고리즘

### 5.1. 랭킹 집계 쿼리

* 특정 아티스트/멤버별 전체 마스터 카드 수 대비 유저의 `status='OWNED'` 카드 수의 비율(Percentage)을 계산.

### 5.2. 중복 수상 방지 (쿨다운 & 롤다운) 테이블

* **Table: `reward_history**`
* `user_id`, `artist_id`, `reward_quarter` (예: 2026-Q3), `rank`, `is_cooldown` (BOOLEAN).


* **처리 로직:**
1. 분기 마감 크론(Cron) 작업 실행.
2. 상위 1~3위 유저 추출.
3. 추출된 유저 중 `reward_history`에 지난 1년(4개 분기) 내 동일 `artist_id`로 보상을 받은 이력이 있으면 해당 유저를 보상 대상에서 스킵(롤다운)하고 4위 유저를 보상 대상자로 편입.
4. UI 단에서는 해당 1위 유저에게 `[👑 챔피언]` 뱃지는 정상 노출하되, 실물 보상 팝업은 미노출.

## 6. [법무 검토] 서비스 초기 포인트/리워드 지급에 대한 법적 리스크

마이크로 인플루언서 제휴 리워드 및 유료 결제 환급액 10% 적립 등 MVP 초기 플랫폼 내 포인트 지급 행위에 대한 한국 전자금융거래법(전금법) 및 규제 검토안입니다.

### 6.1. 핵심 법적 쟁점: 선불전자지급수단 해당 여부

유저에게 포인트를 지급할 때, 이 포인트가 '선불전자지급수단'으로 분류되면 금융위원회에 선불업자로 등록해야 하는 막대한 규제 리스크(자본금 20억 요건 등)가 발생합니다. 이를 회피하는 것이 최우선 과제입니다.

### 6.2. 규제 회피를 위한 시스템 설계 가이드 (안전망)

포인트 제도를 운영하되 선불업 등록 의무를 면제받으려면 약관과 DB 구조가 다음 조건을 충족해야 합니다.

1. **환급성(현금화) 원천 차단:**
* 포인트는 서비스 내에서 연간 유지비 결제, 향후 오픈될 K-POP 앨범 공동구매, 에스크로 수수료 할인 용도로만 사용 가능해야 합니다.
* 유저가 포인트를 자신의 은행 계좌로 현금 출금(Cash-out)할 수 없도록 **약관에 "본 포인트는 회사 내 서비스 이용을 위한 재화로, 현금으로 환급 불가합니다"라고 명시**해야 합니다. (이 경우 단순 마일리지/쿠폰으로 분류되어 전금법 적용 배제).


2. **포인트의 출처 분리 (유상 vs 무상 포인트):**
* 유저가 '돈을 주고 충전한 포인트(유상)'와 '활동/제휴 리워드로 무상 지급받은 포인트(무상)'는 DB 상에서 엄격히 분리(`point_balance_paid`, `point_balance_free`)되어야 합니다.
* 무상 포인트는 전금법상 보호 대상이 아니므로 규제에서 완전히 자유롭습니다. MVP에서 지급하는 인플루언서 성과급이나 10% 적립 포인트는 전량 '무상(프로모션) 포인트'로 약관에 정의하십시오.


3. **인플루언서 현금 정산의 예외 처리 (B2B 제휴 정산):**
* 인플루언서 50인에게 성과급을 '현금'으로 지급하는 것은 '포인트 환급'이 아니라 마케팅 대행에 대한 용역비(B2B 정산, 3.3% 사업소득 원천징수 대상)로 회계 처리해야 합니다. 플랫폼 내부 포인트 시스템과 회계상 완전히 분리하여 지급하십시오.



### 6.3. 법무 적용 결론

MVP 단계에서는 유저 지갑(`user_wallets` 테이블)에 적립되는 모든 재화를 'StanPC 내에서만 사용 가능한 프로모션 리워드(현금화 불가)'로 정의하여 약관에 명시함으로써 복잡한 금융 규제를 100% 우회하고 합법적으로 마케팅/보상 시스템을 가동할 수 있습니다.

## 7. 보안 및 결제 아키텍처 (Security & Billing)

### 7.1. 결제 데이터 무결성 (Stripe)

* 웹-퍼스트 결제 시 Stripe Checkout Session을 생성하고, 서버의 웹훅(Webhook)을 통해 결제 완료(`checkout.session.completed`) 이벤트를 수신합니다.
* 웹훅 처리 시 Stripe의 Signature 시크릿 키 검증을 필수로 구현하여 허위 결제 승인 요청을 차단합니다.

### 7.2. 행 단위 보안 (Row-Level Security, RLS)

Supabase의 PostgreSQL 스키마에 다음 RLS 정책을 강제 적용합니다.

* **Inventory 조회:** 본인의 데이터(`auth.uid() = user_id`)만 조회 가능. 단, 유저가 프로필을 공개(`is_public = true`)한 경우 다른 유저도 `status`, `image_url` 등 민감하지 않은 데이터만 `SELECT` 가능.
* **Inventory 수정/삭제:** 오직 데이터 소유자(`auth.uid() = user_id`)만이 `UPDATE`, `DELETE` 권한을 가짐. API 클라이언트 변조를 통한 타인 포카 삭제를 원천 방어.
